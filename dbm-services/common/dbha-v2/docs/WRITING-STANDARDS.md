# dbha-v2 文档写作与检查规范

本文档是 dbha-v2 项目所有 Markdown 文档（含 README、CODEBUDDY、docs/ 下各篇）的写作与检查标准。撰写新文档、修改既有文档、评审文档时必须逐条遵守。凡与代码相关的表述，以代码为唯一事实基准。

## 1. 结构清晰

- 标题层级不跳级：H2 之下只出现 H3，不出现直接从 H2 跳到 H4 的情况。
- 章节顺序遵循「是什么 → 为什么 → 怎么做 → 参数与排障」的顺序；读者按顺序读完即可复现操作。
- 正文中引用的图、表、代码段就近放置，不跨章节引用。
- 文档若包含目录，目录条目必须与实际章节标题一一对应。

## 2. 内容完整

- 标题或引言中承诺的内容，正文必须全部兑现；不能出现「详见下文」而下文不存在的引用。
- 所有命令、参数、文件路径、指标名、事件名、函数名、配置键必须真实存在，可以在代码或配置中查证；写完后亲自执行或核对一遍。
- 示例必须可以照抄执行：命令示例包含必填参数；配置示例是合法语法；路径示例与实际目录结构一致。
- 引用的其他文档或代码位置必须存在；相对链接和锚点必须有效。
- 不写「略」「此处省略」这类让读者无法复现的省略。

## 3. 文字流畅、通俗易懂、无废话

- 一句话只表达一件事。超过约 60 个汉字的句子必须拆分。
- 删除同义反复：同一信息只在一个地方完整陈述，其他地方用链接或一句话回指。
- 删除空话：不写「本章节旨在介绍」「综上所述」「值得注意的是」这类不提供信息的句子。
- 术语第一次出现时给定义或链接，之后保持一致，不中途换叫法。
- 优先写「是什么、怎么做」，少说「多么好」。

## 4. 无 AI 味儿、标点正确

- 禁用以下套话与句式：赋能、落地（作动词指交付时除外，须看语境）、优雅、高效地、无缝、值得注意的是、总而言之、众所周知、不仅……更是……、在……的世界里、让我们一起来看看。
- 中文句子用中文标点：，。；：「」（）、。英文单词、代码标识符、命令行内部保持半角。
- 冒号后面如果是完整句子，就独立成句，不要硬接在冒号后不换行。
- 不滥用省略号和感叹号；一个文档中感叹号不超过一处，且只用于真正的警告。
- 数字、英文、代码与中文之间不加多余空格以外的修饰，保持朴素。

## 5. 语句结构完整、指代清楚

- 表达核心结论的句子必须有完整的主语、谓语、宾语，不写半截话。
- 「其」「该」「这」「上面」「后者」必须有唯一明确的先行词；无法明确时重复名词。
- 表格每一行的主语要和该表格说明的对象一致；表格第一行不出现没有来源的「它」。
- 编号步骤的每一步都是完整可执行的动作，含动作主体和对象。

## 6. 配图与文章内容匹配且正确

- 正文中引用的每张图必须真实存在于仓库，路径正确。
- 图中的节点、分支、标签文字必须与代码中的调用链、函数名、事件名、阈值、分支条件一致。
- 图内的文字必须与正文及「色例」说明一致；配色语义逐图绑定，不跨图套用。
- 图中不得出现代码中不存在的符号、函数名或目录名。
- 图下方必须有色例或图例说明，说明与图中实际使用的颜色一一对应。
- 时序图的消息文字、流程图的分支条件必须与代码真实分支一一对应。

## 机械可检查项

以下项目可以用脚本机械检查，修复后应复跑清零：

- 相对链接与同页锚点是否有效。
- 中文句中是否混入半角逗号、句号、冒号；代码块外是否用英文括号包中文。
- 是否存在超过 60 字且无法分句的长句。
- 是否命中禁用词表。
- 表格列数是否与表头一致；标题是否跳级；是否有空标题。

## 人工判断项

以下项目需要人工评审，脚本无法完全替代：

- 段落之间的逻辑顺序是否顺。
- 是否存在读者读完后仍不知道「下一步做什么」的章节。
- 指代是否清楚；术语是否前后一致。
- 图的内容是否真的和正文说的是同一件事。

## 适用范围与执行

- 适用：dbm-services/common/dbha-v2 下所有 Markdown 文档，以及 docs/assets/diagrams/ 下所有 SVG 配图的文字内容。
- 执行：撰写或修改文档时先对照本规范自查；评审文档时逐维度检查；发现违反项必须给出「文件:行号 → 问题 → 建议改法 → 级别（必须修/建议修/可不修）」的记录。
- 事实性内容一律以代码为准，不凭记忆或惯例编写。
