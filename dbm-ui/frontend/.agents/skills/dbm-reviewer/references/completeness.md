# 功能完整性检查项

回答的问题：这次改动要做的事，做全了没有。每次审查都读。

## 先定「要做什么」

依次找需求来源：用户在对话里的说明 → `openspec/changes/` 下对应的提案与任务清单 → commit message、分支名。
都没有时按 diff 推断，并在报告开头写明推断出的改动意图，让用户能纠正。

需求没写的不算缺失：不要把「我觉得还应该有」的功能立成问题，拿不准的放进「待人工验证」。

## 需求对照

把需求拆成条目，逐条找到实现位置：

- 需求点没有对应实现，或只实现了主路径，需求里写明的分支场景没做；
- 需求要求改多处（多个页面、多个 DB、多个入口），只改了其中几处；
- 实现了需求没提的额外行为，且会改变现有功能。

## 半成品痕迹

只看本次新增的行：

- `TODO` / `FIXME`、被注释掉的代码块、空函数体、空的事件回调；
- 写死的假数据、mock 返回、写死的 id 或业务号、写死的环境地址；
- 调试残留：`console.log`、`debugger`、临时开关；
- 占位文案、未翻译的文案；新增 `t()` 文案在 `src/locales/` 的语言包里没补条目，英文环境会直接显示 key。

## 状态覆盖

新增或改动的界面、流程，除了成功路径还要看：

- 加载中、空数据、请求失败各自有没有处理；
- 无权限、功能关闭、禁用态下的表现；
- 表单的必填与格式校验、提交失败后的状态；
- 边界输入：空、超长、0、负数、重复项、数量上限。

## 成对的另一半

- 新增了创建，查看 / 编辑 / 删除是否需要跟上；新增了提交字段，回显与详情展示是否跟上；
- 加了打开没加关闭，加了订阅没加退订，加了开始没加结束；
- 新增页面是否有可达的入口；新增入口点进去是否有对应页面；
- 联合类型、枚举新增成员后，按它分支的 `switch` 与映射表没补分支；
- 改了字段名或数据结构，读写两端是否都改了。

各模块「新增一个 X 要登记哪些地方」的清单在对应场景 skill，按 SKILL.md 第 2 节的表加载后照着核，本篇不重复。

## 定级与写法

- 需求点缺失、主流程走不通：P1；
- 半成品痕迹：假数据、调试开关会影响线上行为的 P1，其余 P2；
- 状态覆盖缺失：按触发概率与后果定 P2 / P3；
- 缺失类问题没有对应的 diff 行，条目指向应当补上的位置（文件，或最接近的行）。
