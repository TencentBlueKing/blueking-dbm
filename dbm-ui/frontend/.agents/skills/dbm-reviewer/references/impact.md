# 连带影响检查项

回答的问题：这次没改到的地方，会不会因为这次改动出错。答案不在 diff 里，必须走出 diff 去读引用点。

## 查法

1. 列出本次改动的对外面：被导出的函数 / 类型 / 常量，组件的 props / emits / 插槽 / `defineExpose`，store 的 state
   与 action，路由 name 与参数，接口的入参与返回，全局样式与公共类名，事件名，本地存储的 key；
2. 对每一项查引用点：仓库有 `.codegraph/` 时用 `codegraph explore "<符号名>"`，否则用 `rg`。动态拼出来的引用
   （按变量取枚举、模板字符串拼路由 name、按名字解析组件）搜不到，要按拼接规则另找；
3. 逐个读引用点，判断旧用法在新行为下是否仍然成立；
4. 改了 `components/`、`hooks/`、`services/` 的公共行为时，引用点要穷举。报告里写明查了多少处、哪些没展开；
   抽样了就写「抽查 N 处」，不写成「调用方均不受影响」。

## 签名没变、行为变了

最容易漏，因为类型检查不会报：

- 默认值变了；返回值在某些分支下从有值变成 `undefined` / 空数组，或数组变成对象；
- 同步改异步而调用方没有 `await`；原来 reject 现在 resolve（或反过来），调用方的 `try/catch`、`finally` 语义跟着变；
- 原地修改了入参，或返回了内部状态的引用，调用方的数据被悄悄改掉；
- 触发时机变了：`emit` 提前或延后、从「值变化时」变成「每次」、`watch` 加了 `immediate`；
- 条件收紧或放宽：原本对某些入参直接返回的，现在往下走了。

## 契约变了

- 函数签名、props、emits、插槽参数、`defineExpose` 的增删改名：所有使用方是否同步；新增的 prop 有没有默认值，
  老调用方不传时行为是否不变；
- store 的 state 结构、getter 语义变了：所有读取方；
- 路由 name、params、query 变了：`router.push` / `router.resolve`、菜单、外链，以及已经发出去的链接（收藏、通知里的地址）；
- 本地存储的 key 或数据结构变了：用户浏览器里的旧数据读出来会不会崩，要有兼容或清理；
- 接口入参、返回字段变了：同一接口的其它调用点，依赖该字段的 model 与计算属性；
- 类型、枚举、常量的增删改值：按它分支的映射表与 `switch`。映射表声明成 `Record<枚举, T>` 可以让编译器拦住。

## 删除与守卫

- diff 删掉了条件分支、守卫或标志位：能否复述它原本区分什么，说不清就按 P1 报，不默认是历史残留；
- 删掉的函数、组件、样式、语言包条目是否还有引用，含动态引用；
- 一个入口承担多种调用意图（如条件变更 / 原地刷新）时，新判据是否覆盖全部意图，而非只覆盖当前场景。

## 共享状态与样式

- 改了被多个组件共用的 store、模块级变量的写入时机或取值；模块级变量在多个组件实例间是共享的；
- 非 scoped 样式、全局类名、公共 less 变量的改动会波及其它页面；
- 改了公共组件的 DOM 结构或 class，外部依赖该结构的 `:deep()` 样式失效；
- 全局注册的指令、事件总线的事件名、`provide` 的 key 改动后，另一端是否同步。

## 同构实现

- 同一逻辑有多份拷贝（多个 DB 的同类页面、新旧两套组件、业务页与平台页），本次只改了一份；
- 修的是一个 bug 时，同样的写法在别处是否也有。别处的属于存量，写进「残余风险」，不立项。

## 怎么报

连带影响类问题，条目指向引起它的改动行，受影响的引用点写在说明里。
