# 全量扫描模式

用户要求扫描某个目录（如 `src/views`、某个 DB 的工具箱）而不是审本地 diff 时使用。产出是缺陷报告，不改代码。

## 1. 先划范围、定深度

- 列出一级模块和文件数，大模块（`db-manage`、`ticket-center` 这类上千文件）只能按模式扫，要在报告开头写明
  「这不是逐行审阅」，并在每个模块的「残余风险」里说清没展开的业务分支
- 每个模块一份报告，外加一份总览（总数、各模块结论、P1 清单、扫描时排除的项）

## 2. 按模式检索，再读上下文

先用 `rg` 按 SKILL.md 第 5 节的模式检索，命中后**必须读上下文**再决定是否立项。常用检索：

```bash
rg -n "innerHTML\s*=" src/views
rg -n "JSON\.parse\(decodeURIComponent" src/views
rg -n "\?\.\[0\]\.[a-z_]" src/views
rg -n "useCreateTicket<" src/views                              # 逐个看是否在工具箱页、是否传 isToolbox: false
rg -n "\|\| '--'" src/views
rg -n "window\.open\(href\)" src/views                          # 业务路由是否需要 getBusinessHref
rg -n "setInterval\(" src/views                                 # interval 变量是否在组件作用域并在卸载时清理
rg -n "v-model\.[a-z]+" src/views | rg -v "\.(trim|number|lazy)"
```

## 3. 立项前核对

SKILL.md 第 4 节「立项前必须核对的三件事」在全量模式下同样强制，且要额外核：

- 两份同名实现（资源池 / 普通目录、业务 / 平台页）是否真的都会被渲染，先看选择逻辑
- 跨层结论（「后端会拒绝」「接口会忽略」）必须读 `dbm-ui/backend` 代码后再写，写明文件位置
- 统计类结论（「36 个同名组件」「30 处回填只带 id」）给出复现命令或清单，便于复核

## 4. 定级

- P0：存储型 XSS、必然白屏且无法自恢复（如坏缓存导致整页起不来且不清缓存进不去，可视影响面定 P0 / P1）
- P1：错误数据被提交、操作失败无任何反馈、跳错业务或打不开页面
- P2：需要特定数据或时序才触发的崩溃（历史单据、竞态）、被校验拦住的回填缺失、显示错误
- P3：文案、排序、视觉不一致

被校验拦住、入口已门控、后端兜底的，按实际影响降级，不按「代码看起来会怎样」定级。

## 5. 报告格式

与 SKILL.md 第 6 节一致，另加两段：

- **核对过、不构成缺陷**：查过但能自圆的点，写清理由，避免下一轮重复立项
- **扫描时排除的项**：按模式检索为 0 或全部自圆的模式，写在总览里
