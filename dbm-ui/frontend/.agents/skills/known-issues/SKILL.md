# known-issues

两层：`checks.md` 是索引，一条一行、只放「什么时候命中」，改代码前整份扫一遍；`doc/<topic>.md`
是细节，写清「命中 / 为什么 / 改成 / 不要 / 存量 / 核实」，只打开命中条件对上的那几篇。

分层是为了改代码前那一次扫描足够便宜——索引会一直读，细节只按需读。

目标是同一个问题用户只说一次。所以每条检查项必须写到能被下一个 agent 直接执行的程度：判据具体到能在代码里搜出来，改法具体到能照抄。写成「注意保持一致」这种执行不了的话，等于没写。

## 先判断该放在哪个面上

写进 `checks.md` 之前先问一遍：**这条能不能不靠模型注意力就生效？** 能就别写进清单。清单是软约束，长会话里必然有漏扫的时候；工具是硬约束，跑到就报错。

优先级从高到低：

1. **类型收窄**——能让 TS 在编译期拦下的，改类型声明。例：`MultipleSelect` 的 `value` 声明成 `string`
   而不是 `string | string[]`
2. **ESLint 规则**——语法形态固定、能写出 esquery 选择器的，加 `no-restricted-syntax`，`message`
   里写清后果并指向对应 doc。存量违规不用先修：`lint-staged` 只查 `git add` 的文件，规则会在有人真的编辑到那个文件时才拦下来，正好等于「本次碰到就修掉」
3. **`checks.md` 条目**——上面两条都做不到才写进清单

已经下沉的条目从 A / B 两段里删掉，只在「已下沉到工具」那段留一行说明去向，防止后来者再加回来。

## 时机一：改代码前对照

动手改 `src/` 下任何文件前，扫一遍 `checks.md`。A 类按代码特征判断，B 类先比路径前缀，对不上直接跳过。

**扫完在回复里固定写一行 `known-issues: 已扫，命中 N 条`，N 为 0 也要写。** 没有这一行，用户无法区分「没命中」和「压根没扫」，清单的失效会一直不被发现。

修改边界是硬的：

- **本次改动已经碰到的代码**里命中 A 类 → 按条目给的改法直接修掉，在回复里说一句改了什么
- **同文件其它位置、或其它文件**里命中 → 只报告，不动手，等用户决定
- B 类（改法未定）→ 一律只报告

这条边界与 AGENTS.md 的「只改与当前任务直接相关的代码」「不顺手优化相邻代码」一致。检查项不是顺手清理全仓库的许可。

## 时机二：用户指出问题时写入

用户在对话里说「这里应该这么写」「这个写法不对」「这块要优化」，就是触发点。**当场做，不要留到收尾**——收尾时上下文已经稀释，提炼出的判据会失真。

1. **判断能不能推广**。只对当前这一处成立的（业务逻辑、本页面的特定需求）不记；能推广成「以后遇到同类代码都该这么写」的才记。出现次数不是判据，第一次出现也可以记，只要改法是通用的。

2. **判断该放在哪个面上**。见上一节，能下沉成类型或 ESLint 规则的优先下沉。

3. **横向排查**。用判据在本次没碰到的文件里搜一遍，确认还有多少处。这一步决定两件事：本次要不要提醒用户同步改，以及条目里「存量」怎么写。搜不到别的实例也照样记，判据本身就是价值。

4. **写入**。先扫 `checks.md` 看有没有同主题条目，有就补进它的 doc，不新开一条；确实是新主题才建
   `doc/<topic>.md` 并在 `checks.md` 补一行索引。

### 判据合格的自检

**把这条判据交给一个没参与本次对话的 agent，它能不能在代码里搜出命中点？** 唯一可靠的验证方式是**自己把命令跑一遍，看输出对不对**。

- 合格：`rg -n '(const|let) \w+ = await [^;]*\.validate\(' src`
- 合格：`<BkPagination>` 上有 `v-bind="pagination"` 且同一标签没有 `:model-value`（附上能跑的 rg 命令）
- 不合格：校验写法要统一 / 注意分页状态同步（都搜不出来）
- 不合格：`setTimeout(..., 210)`——看着像能搜，实际代码跨行，按这个形状搜是 0 命中

改法同理，要能照抄，不能只给方向。

## 格式

`doc/<topic>.md`：

```markdown
# <一句话说清是什么问题>

- **命中**：能直接复制执行的 rg 命令，或具体到能搜出来的代码特征。也可以是「你正要新增 X」这种防重复的时机
- **为什么**：一句话说清后果。用户能看到或维护者会踩到的后果，不是「不优雅」
- **改成**：能照抄的写法。没把握就写「未定，命中只报告」
- **不要**：试过或想过但不该做的方案 + 原因。防止后来者把「只报告」的条目当成重构许可
- **存量**：一条能重新跑出当前列表的命令；数量不多时补一份 `src/` 开头的全路径清单
- **核实**：最后一次逐条跑过命令、读过代码的日期

## 补充

排查过程、对比表。执行不需要读到这里，可选。
```

`checks.md` 索引行：命中条件要写到**不打开 doc 就能判断这次改动相关不相关**——给得出路径就把路径写在前面，给不出就给代码特征。

## 纪律

- 写进条目的每个数字、每个路径都要亲自跑命令 / 读文件确认过，不能凭 grep 计数或印象推断。写完更新「核实」日期
- **不写行号**。路径一律从 `src/` 写全，定位靠可搜的字符串或 rg 命令。行号会在下一次重构里静默失效，而失效的引用比没有更糟——它会让后来者以为自己找错了地方
- 改法没验证过就标「未定」，不要给一个自己也没把握的写法让后来者照抄
- 已修复且不可能再复发的条目直接删（比如源目录已整体删除），留着只会稀释清单
- 不记单点 bug、个人风格偏好、以及 ESLint / Prettier / Stylelint 能自动修的问题。清单一旦注水就没人看了
- 一个主题一篇 doc。同主题往已有 doc 里补，不新开一篇
- `checks.md` 只放索引行，细节一律进 doc。索引每条一行，不许长成第二份文档

### 复查

发版前，或任何条目的「核实」日期超过一个月时，把所有 doc 的命中 / 存量命令重跑一遍：命令输出为空的条目直接删，路径不存在的条目就地改掉，然后更新「核实」日期。

这一步不是可选的。清单腐烂的速度比想象中快——一次重构就能让一整篇 doc 的路径全部失效，而没人会主动发现。
