# MySQL 授权

## 单据名称：【MySQL 授权】

---

### 1. 单据基本信息

**单据描述**：

- 单据是用于**统一、规范地申请和管理MySQL数据库访问权限**的流程工具。它将复杂的MySQL原生权限命令（`GRANT`）封装成简单的“账号-授权规则模版-授权”三步操作，实现权限的标准化、模板化和流程化。

**核心价值**:

- 对管理员/运维：化繁为简，通过“授权规则”模板确保权限一致性，避免手动输入命令出错，提升维护效率和安全性。
- 对开发/申请者：无需了解复杂的MySQL权限语法，通过清晰的下拉选择即可完成权限申请。

**适用场景**：

- 新项目/应用上线：需要为应用创建新的数据库账号并授予相应权限
- 服务器/IP变更：应用服务器迁移或扩容后，需要为已有的账号添加新的访问来源IP。
- 权限统一管理：当一个用户（如`report_user`）需要在多个集群上拥有**完全相同**的权限时。
- 集群批量授权：需要为多个目标集群快速授予相同权限组合时，可使用“导入授权”功能。“导入授权”位于“集群视图”页面。
- 来源IP批量授权：希望使用通配符 (%) 授权一批IP，先录入到白名单中，再对其授权，“授权白名单”位于“权限管理”。

**不适用场景**：

- 超级管理员权限申请： 如 `ALL PRIVILEGES` 或 `GRANT OPTION` 等高风险权限不在可选择的权限范围中，需联系业务DBA特殊处理。
- 为一个业务下的同一账号设置不同密码：平台强制规定一个业务下同一账号名在所有集群 必须使用同一密码。例如，出于安全和管理考虑，无法为“测试集群”和“正式集群”上的同一个账号设置不同的密码。

**执行频率**：

- 高频

**影响范围**：

- 重要程度：高
- 主要用户群体：运维 、开发 、 DBA

### 2. 单据流程

#### 完整流程图

```mermaid
graph TD
    A[开始：申请DB访问权限] --> B{账号是否存在？}
    B -- 否 --> C[新建账号]
    C --> D[设置账号密码<br>（需牢记，平台不保存）]
    D --> E
    B -- 是 --> E{账号已有授权规则模版？}
    E -- 否 --> F[新建授权规则模版]
    F --> H
    E -- 是 --> H[执行授权申请]

    H --> I[选择：<br>1. 访问源IP<br>2. 目标集群<br>3. 账号<br>4. 访问DB（模版对应）]
    I --> J{系统检查}

    J -- 检查通过 --> K[执行MySQL授权命令<br>GRANT ... ON ... TO username@ip]
    K --> L[授权成功<br>流程结束]

    J -- 检查失败 --> M{错误类型分析}
    M -- 密码不一致 --> N[提示：账号密码必须统一<br>或者新建独立账号]
    N --> O[流程终止]

    M -- 权限冲突<br>（DB范围重叠） --> P[提示：conflict with applied db [xxx]<br>建议检查现有权限]
    P --> Q[连接集群执行 SHOW GRANTS]
    Q --> R{现有权限是否满足？}
    R -- 是 --> S[提示：权限已存在<br>无需重复申请]
    S --> O

    R -- 否， 需扩大权限DB范围 --> T[提示：标准流程不支持<br>需联系DBA特殊处理]
    T --> O

    R -- 否， 需补充权限类型 --> U[编辑授权规则模板<br>增加权限项]
    U --> H[重新提交申请]
```

### 4. 典型单据报错

- **故障点1**：账号密码不一致
  - 触发条件：集群中mysql用户的密码与dbm平台上设置的账号密码不一致
  - 错误特征：`apply userdemo@1.1.1.1: password not match`
  - 影响范围：授权失败
  - 处理方案：
    - **最佳实践**：确认密码不一致原因，统一密码，确认集群中账号是否在用，如果需要调整集群中的账号密码，需联系业务DBA特殊处理
    - **替代方案**：创建新的独立的账号进行隔离。
    - **特殊处理**：如情况特殊必须处理，比如新建的未被使用的账号，密码设置错误，需联系业务DBA特殊处理

- **故障点2**：授权的访问DB
  - 触发条件：新申请权限的目标数据库范围（授权规则模版中定义的访问DB，如 db%），与该账号在此集群中已有权限的数据库范围存在重叠（交集）。平台为避免权限覆盖，会阻止此类申请。
  - 错误特征：申请失败，并收到如下格式的错误提示：
    - `apply userdemo@1.1.1.1 on db%: conflict with applied db [db1]`（释义：申请对 `userdemo@1.1.1.1` 在 `db%` 范围内授权，与此账号已生效的 `[db1]` 数据库权限存在冲突。）
  - 影响范围：当前授权申请失败，无法执行。
  - 处理方案：
    - 1. **检查现有权限**：登录到目标MySQL集群，执行 `SHOW GRANTS;` 命令，或者用“权限管理”-“权限查询”单据查询，**仔细核对**该账号当前已被授予的**具体数据库**和**详细权限**。
    - 2. **情况一：权限已满足，无需新授权**
      - 如果检查发现，现有权限**已经覆盖**了本次申请的需求（例如，已对 `db1`、`db2` 拥有所需权限），则**本次申请可终止**，直接使用现有权限即可。
    - 3. **情况二：权限类型不足，需补充**
      - 如果现有权限的**数据库范围满足**，但**权限明细不足**（例如，已有 `SELECT` 权限，但本次需要 `CREATE` 权限）。
      - **操作**：可以在平台内**编辑**对应的“授权规则”模板，增加所需的具体权限（如 `CREATE`），然后**重新提交授权申请**。
    - 4. **情况三：需要扩大数据库授权范围**
      - 如果现有权限的**数据库范围不满足**需求（例如，当前仅有 `db1` 权限，但业务确实需要 `db%` 的通配权限）。
      - **说明**：由于平台设计上为避免权限被意外覆盖，**标准授权流程不支持直接修改已授权数据库的范围**。
      - **操作**：此情况无法通过标准单据处理。需**联系业务DBA进行线下评估与特殊处理**，由DBA在数据库侧直接操作调整权限。
