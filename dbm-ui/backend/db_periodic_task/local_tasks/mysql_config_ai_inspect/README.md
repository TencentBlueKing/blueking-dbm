# MySQL 配置 AI 巡检评分规则

## 1. 适用范围与职责

本规则用于周期巡检 `mysql_config_ai_inspect` 产出的画像 `CONFIG_CHECK` 维度分数，适用于 `TenDBSingle`、`TenDBHA`、`TenDBCluster`。

- 规则版本：`config_check_v1`。
- 分数范围：0～100，越高越健康；`None` 表示无法评分，不等于 0 分。
- AI 负责识别问题、判定严重度并提供证据；后端负责校验、去重和确定性算分，不采纳 AI 自行给出的分数。
- 本规则不适用于其他巡检维度，也未接入告警触发的配置分析链路。

实现入口：[scoring.py](./scoring.py) 中的 `calculate_config_score()`；AI 输出要求及画像上报位于 [tasks.py](./tasks.py)。

## 2. 哪些问题需要计分

只有有明确依据、确实构成风险或具有优化价值的独立问题才纳入 `findings`。必须包含本次完整报告中的全部此类问题，不能只统计摘要中提到的部分。

| 严重度 `severity` | 判定标准 | 每个独立问题扣分 |
| --- | --- | ---: |
| `high` | 有明确证据支持的数据可靠性、服务可用性或严重资源风险 | 15 |
| `medium` | 有明确依据的非紧急性能、稳定性或配置一致性问题 | 5 |
| `low` | 有依据的轻量优化建议，当前运行影响有限 | 1 |

判定要求：

1. 结合实例角色、版本、机器规格、资源使用情况及已知业务要求判断，不能仅凭偏离某个推荐参数值就认定高危。
2. 合理的角色差异、架构差异和业务配置取舍不扣分。
3. 未知业务要求或缺少证据的推测，写入报告的待确认事项，不纳入扣分；如果因此无法完成核心检查，必须标记数据不足。
4. 同一根因涉及多个关联参数时，应合并为一个问题，不对每个参数重复扣分。
5. 无效或缺失的严重度不默认为 `low`，而是使本次评分不可用。

后端校验结构、必填内容和枚举值，不自动验证证据的真实性或业务判断的合理性；这些仍依赖 AI 分析及后续抽样校准。

## 3. 评分前提：核心检查完整

`checks` 必须是对象列表，完整且不重复地包含以下三个检查项。不允许遗漏、重复或增加未知检查标识。

| 检查标识 `code` | 检查内容 |
| --- | --- |
| `config_rationality` | 配置与机器规格、实例角色、资源使用情况是否匹配 |
| `config_consistency` | 主从、同角色节点或分片之间是否存在不合理配置差异 |
| `version_compatibility` | 参数是否适用于当前版本、引擎和集群架构 |

每项必须包含 `code`、`status` 和非空字符串 `reason`。`reason` 应说明检查依据，或无法检查、不适用的原因。

| 状态 `status` | 含义 | 是否允许评分 |
| --- | --- | --- |
| `completed` | 已完成检查，不代表没有问题 | 是 |
| `not_applicable` | 当前架构不适用 | 仅允许 `TenDBSingle` 的 `config_consistency` 使用，并说明没有可比较实例的原因 |
| `insufficient_data` | 数据不足，无法完成检查 | 否，整个维度不评分 |

只有三项都通过校验，且问题列表也有效，才能生成分数。检查完成且 `findings` 为空列表时可得 100 分；遗漏检查项或没有足够数据时，不能以“没有发现问题”为由给 100 分。

## 4. 问题列表与去重规则

### 4.1 问题字段

每个 `findings` 元素必须是对象，并包含以下字段：

| 字段 | 要求 |
| --- | --- |
| `issue_key` | 稳定问题标识，按风险类型、排序后的参数组、适用角色生成，不应包含 IP、分片号等实例标识 |
| `category` | 只能是 `durability`、`resource`、`consistency`、`version_compatibility`、`performance` |
| `parameters` | 非空字符串列表，列出关联参数 |
| `scope.role` | 非空字符串，说明适用实例角色 |
| `scope.instances` | 非空字符串列表，列出受影响实例；AI 输出要求使用 `ip:port` |
| `severity` | 只能是 `high`、`medium`、`low` |
| `evidence` | 非空字符串，提供当前值、对照依据及必要的运行上下文 |
| `impact` | 非空字符串，说明风险及影响 |

`issue_key` 去除首尾空白并转为小写后，必须匹配 `[a-z0-9][a-z0-9_.:+-]*`。例如 `connection_capacity:max_connections:master`。

后端只校验标识的字符格式，不解析其风险类型、参数组、角色之间的语义关系；`scope.instances` 也只校验非空字符串列表，不验证实际实例地址。

`category` 用于分类和去重冲突校验，不设单独权重或类别扣分上限。

### 4.2 去重步骤

1. 将 `issue_key`、`scope.role` 去除首尾空白并转为小写；参数名同样规范化，并去重、排序。
2. 按 `(issue_key, scope.role)` 分组。同一问题影响多个实例或分片，只扣一次，不乘以受影响实例数量。
3. 同组条目的参数组和类别必须一致，否则视为评分依据冲突，本次评分不可用。
4. 同组严重度不一致时取最高级别，并合并受影响实例集合。
5. 不同角色的问题分别计分；不同 `issue_key` 不会由后端进行语义合并。
6. 扣分明细的 `source_indices` 保留原始 `findings` 中从 0 开始的索引，便于追溯合并来源。

AI 必须先完成同根因问题合并并生成稳定标识，后端再做结构化去重。若同一个问题被 AI 赋予不同标识，当前实现无法自动识别，需通过样本校准改进输出。

## 5. 计分公式

设去重后的高、中、低严重度问题数分别为 \(H\)、\(M\)、\(L\)。

总扣分：

\[
D = 15H + 5M + L
\]

基础分：

\[
S_{\text{base}} = \max(0, 100 - D)
\]

最终分：

\[
S = \begin{cases}
\min(S_{\text{base}}, 60), & H > 0 \\
S_{\text{base}}, & H = 0
\end{cases}
\]

- 存在 `high` 问题时，最终分不超过 60；不是固定为 60，也不是额外固定扣 40 分。
- 不设置类别扣分上限，最低为 0 分。
- 当前计算结果为整数值，但以浮点数返回并保存到可空 `FloatField`。
- 当前实现只计算分数，未实现“健康／需关注／有风险”等分档。

### 计分示例

除最后两行外，均假设核心检查和问题字段有效，问题数量已经去重。

| 情况 | 基础分 | 最终分 |
| --- | ---: | ---: |
| 无问题 | 100 | 100 |
| 2 个 `medium`、3 个 `low` | 87 | 87 |
| 1 个 `high` | 85 | 60 |
| 1 个 `high`、2 个 `medium` | 75 | 60 |
| 4 个 `high` | 40 | 40 |
| 10 个 `high` | 0 | 0 |
| 同一个 `medium` 问题影响 100 个分片 | 95 | 95 |
| 同一去重组分别上报 `medium` 和 `high` | 85 | 60 |
| 任一核心检查数据不足 | 不计算 | `None` |
| 严重度非法、缺少证据或问题标识冲突 | 不计算 | `None` |

## 6. 不可评分与兼容处理

报告成功与评分成功分开判断。只要报告信息有效，下列情况不使报告失败，也不额外重试 AI：

- 旧版输出只有 `report_id`、`share_url`、`summary`，没有 `checks` 或 `findings`。
- 核心检查遗漏、重复、标识或状态非法、缺少依据、数据不足，或不满足“不适用”的架构条件。
- 问题列表类型错误，问题必要字段、严重度、类别或影响范围无效，或同一去重组存在冲突。
- 评分数据包含 `NaN`、无穷大等无法安全保存为 JSON 的值。
- 仅通过正则兜底恢复了报告信息，没有取得完整的结构化评分数据。

上述情况返回 `score=None`，在评分依据中记录错误，并仍上报报告摘要和详情链接。不能用 0 分代替未知，也不能从摘要文字中猜测扣分。

[parse_result.py](./parse_result.py) 仅从完整 JSON 或 JSON 代码块中提取评分字段。报告信息本身解析失败时，仍沿用原有巡检失败、重试机制。

## 7. 保存与画像上报

巡检明细模型 `MysqlConfigAiInspect` 对应表 `tb_mysql_config_ai_inspect`，每条记录代表一个“批次 × 集群”：

| 字段 | 用途 |
| --- | --- |
| `score` | 最终分数；空值表示未评分或无法评分 |
| `score_detail` | JSON 评分依据及计算结果 |

`score_detail` 内容：

| 字段 | 含义 |
| --- | --- |
| `rule_version`、`cluster_type` | 规则版本和本次集群类型 |
| `status` | `scored` 或 `unavailable`，独立于巡检记录的执行状态 |
| `checks`、`findings` | 原始评分输入；缺失字段为 `None`；输入无法安全 JSON 序列化时两者置为 `None` |
| `errors` | 不可评分原因；评分成功时为空列表 |
| `counts`、`deductions` | 评分成功时保存的去重后各级问题数及逐项扣分明细 |
| `total_deduction`、`base_score` | 总扣分及已限制最低为 0 的基础分 |
| `high_risk_cap` | 有高危问题时为 60，否则为 `None` |
| `cap_applied` | 最终分是否因高危封顶而低于基础分；有高危但基础分已不超过 60 时为 `false` |
| `score` | 评分成功时保存的最终分数 |

校验失败时不生成扣分汇总和最终分数字段，只保留可保存的原始输入及失败原因。

执行顺序为：AI 分析 → 解析及算分 → 报告、分数和依据一起条件更新落库 → `ingest_summary(score=row.score)` 上报画像。

画像侧 `PortraitDimensionSummary` 已有 `score` 字段，无需新增。画像上报异常不回滚已成功保存的巡检记录和评分。

字段由迁移 `0057_mysqlconfigaiinspect_score_score_detail.py` 添加，部署使用前需应用迁移。历史记录默认 `score=NULL`、`score_detail={}`，不自动补分。

## 8. 规则维护

- 15／5／1 扣分和 60 分封顶是 `config_check_v1` 的试行口径，应结合真实报告校准，不代表行业统一标准。
- 相同结构化输入使用同一版本规则，后端计算结果一致；AI 的识别结果、定级或问题标识变化仍可能导致分数波动。
- 修改扣分标准、核心检查要求或去重口径时，应同步更新 `RULE_VERSION`、AI 输出要求和本文档，避免历史分数口径混淆。
- 留存的输入可用于复算，但当前没有自动历史重算任务。
